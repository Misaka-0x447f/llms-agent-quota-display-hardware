## 目标（已与用户定稿）

1. 去掉屏幕最下方的状态行，把空间还给三行数据。
2. 每一行做两个视图轮换，各行之间同步切换（同一时刻所有行处于同一视图号）：
   - 视图 1：该行数据（与现在一致）。
   - 视图 2：该行的过期时间 + 状态词，即原来底部状态行的信息。
   - 没有异常的行不存在视图 2（等价于两个视图相同，不轮换）。
   - 视图 2 的过期时间与状态词沿用原状态行的左右布局：左为过期时间，右为状态词。
3. 刷新频率固定：Claude 用量 10 分钟，DeepSeek / OpenRouter 余额 50 秒，各自独立排队。
4. 过期时间显示规则：不足一个刷新间隔时显示 `<间隔`（Claude `<10m`，余额 50 秒折算 `<1m`），
   否则显示向下取整的分钟数（如 `12m`）；没有成功记录或时间不可用时显示 `--`。
5. CLI 与固件协议删除 `--interval` / `--interval-seconds` / `refresh_seconds` / `refresh_minutes`
   （用户已确认）。

## 已确认的产品规则

- 「空闲 / 正常 / 刷新中 / 未配置」都不算异常，不产生视图 2。
- 首次抓取完成前没有异常，不轮换。
- 同一行有多个 key、部分失败时：该行仍算异常，视图 2 显示第一个失败 key 的状态，视图 1 保留 `*`。
- 视图相位每 2 秒切换一次（`kViewHoldMs`），可调。
- 布局保持原来的观感：三行仍相隔 16px，上下各留出半行左右的空闲
  （行基线 20 / 36 / 52，用户上机看过后又要求整体上移 2px）。
- 时钟只依赖 NTP；不拿 API 返回的时间校准设备时钟。NTP 未就绪时剩余时间显示 `--`，不显示假天数。

## 追加需求：1px loading 动画（用户新提出）

- 需求：哪一行正在抓取，就在该行下面画一条 1px 的 Material 风格 indeterminate
  进度条，只占 1px。
- 取舍（用户选择）：请求期间主循环是阻塞的，动画必须放在独立任务里才动得起来；
  用户接受新增一把显示互斥锁和并发逻辑。
- 实现：
  - `row_view.h::loadingBarSpan`（高光位置）与 `loadingBarFlush`（只算需要重发的
    tile 列，新旧位置不相交时拆两段）都是纯函数，配 4 条原生测试。
  - 线在行基线 **+2**（22/38/54），分属 2/4/6 三页；`static_assert` 用实测的
    「最大上伸 11 行、最大下伸 1 行」锁住「不压本行、不压下一行、不出屏、不同页」。
  - 字体上下界用主机端编译 u8g2 实际渲染量出：`[` 顶到基线 −11，7×14 的
    `D-4h`/`27%` 为 −10..−1，6×12 的 `deepseek`/`openrouter` 因 `p` 到 +1。
    所以 +2 紧贴本行、离下一行 ink 还有 2px；+3 会两边各差 1px，反而像属于下一行。
  - loading 动画的开关是独立的 `fetchingMask`（bit0/1/2），只在 `refreshSources`
    里置位、用 RAII 在函数返回时清零；`loadSettings`/`resetBalanceGroup` 不再写
    `kLoading`。这样「刷新循环从未启动」的配置（有 Claude 凭据但没配 Wi-Fi、
    或只配了余额 key）不会留下一条永久转动的线。
  - `drawScreen` 不再画 loading 线，线只由动画任务画/擦，避免「全屏画过但任务
    的 previousX 不知道」造成 boot 残影。
  - `loadingAnimationTask` 每 60 ms 一帧，锁内读一次 `fetchingMask`；每帧只
    `updateDisplayArea` 高光新旧位置覆盖的几列；`displayMutex` 串行化所有显示访问，
    互斥锁或任务创建失败时打印错误并退化为「无动画、照常绘图」。
  - 来源在发起请求前先置 `kLoading`（不算异常，不触发视图 2），抓完立刻覆盖。
- 实测（串口临时埋点，验证后已移除）：软件 I²C 约 1.4 KB/s（一整页 128 B ≈ 90 ms、
  整屏 ≈ 0.9 s）。按 tile 列刷新后的帧成本（含埋点自身约 4 ms/帧的串口开销）：

  请求阻塞期间动画帧连续推进（`REQ` → 收线帧之间没有断档），`fetchingMask`
  也从「联网阶段 7」逐个切到单来源位。

- 帧率优化（用户反馈「帧数很低」后）：原实现每帧把整段 32px 高光重发，改成
  「只刷变化的两端」（`loadingBarFlushDiff`）并把帧间隔 60 ms → 25 ms；
  整段重画只在起步、行数变化、整屏重画之后做一次（`loadingBarNeedsFullFlush`）。

  | 场景 | 优化前 | 优化后 |
  | --- | --- | --- |
  | 单来源 OpenRouter | 11.1 fps / 35 B | 21.5～26.5 fps / 15～16 B |
  | 单来源 Claude | — | 22.1 fps / 16 B |
  | 单来源 DeepSeek | 10.4 fps / 41 B | 17.4 fps / 23 B |

  三行同时抓取时按 3 倍字节估算约 16 fps（未单独采样：WiFi 已连接时批次会
  瞬间从「全部到期」切到单来源，三行同时在刷新的窗口太短）。
- 上机：烧录后 OpenRouter 首次抓取出现一次 `TLS PADLOCK - Input data should be
  aligned`，下一次 50 秒重试即恢复（`age_seconds` 归零），之后多轮抓取正常。
  该现象只在单次出现，未做「临时关掉动画任务」的对照实验，因此**因果未证实**：
  既可能是站点偶发 TLS 失败，也可能是动画任务分走 CPU 的副作用，待复现时再查。

### 用户上机反馈与追加修正（2026-11-12 00:0x）

- 「loading 跑到 deepseek 去了」：**不是缺陷**。当时 Claude 行处于 `TCP被拒绝` 的 10 分钟退避里，屏幕上那条线是 DeepSeek 自己每 50 秒的抓取，位置正确。

  - 修法：`showStatusView(hasError, hasData, phase)` —— 出错但还没有数据的行常驻视图 2，不再轮换；有数据后才恢复 4 秒轮换（当时的相位是 4 秒，2026-11-13 改为 2 秒）。补 `dataless_error_row_never_blinks` 用例。
  - 顺带：没有数据时视图 1 不再整行空白，Claude 行显示 `[--] ... --` 占位，与余额行的 `--` 一致。
- 「c 小写」：视图 2 的 Claude 行平台名改为 `claude`，与 `deepseek` / `openrouter` 一致。

## 追加修正（2026-11-13）：视图轮换 4 秒 → 2 秒
- 用户反馈：「实测两个屏幕之间轮换的时间是 3 秒，应为 2 秒」，并确认口径是
  **每个视图停留 2 秒**（一轮 4 秒），不是「一整轮 2 秒」（每屏 1 秒）。
- 核对实现：`row_view.h` 的 `kViewHoldMs = 4000`，即每个视图停留 4 秒、一轮 8 秒；
  README / firmware README / 本记录都写 4 秒。代码里没有任何 3 秒的相位或调度。
- 关于「为什么读到 3 秒」：**上机实测已排除「设备跑的是 3 秒相位」**。烧录前用 `status`
  采样 `view_phase`（每 400 ms、24 秒）测得相邻转移间隔 4004/4001/4000/4002/4200 ms，
  即旧固件就是 4 秒相位。那句旧记录「每 3 秒采样 1→2→1→2 交替」与 4 秒相位对不上
  （按公式应得 1,1,2,1,2,2），但那次验证跑在提交 909596b 之前的工作区，无法证明当时的常量，
  `status` 也没有固件版本字段，只能存疑。
  用户读到的「3 秒」更符合「画面静止不动的时长」：4 秒相位减去相位翻转时主循环被重画阻塞的
  约 0.45–0.5 秒（本次实机测得 482/484/483 ms），若按这个口径约 3.5 秒，再叠加人工计时与取整
  就是 3 秒上下。「静止段＝相位 − 阻塞时间」本身没有画面录像佐证（u8g2 逐页发送，旧内容不是
  整屏瞬间消失），所以这只是候选解释，不是已确认原因。
- 改动：
  - `firmware/src/row_view.h` 的 `kViewHoldMs` 4000 → 2000（附注释说明来源）；
  - `README.md`：轮换说明改为「每个视图停留 2 秒（一轮 4 秒）」，出错行切换节奏
    与「有数据才轮换」两处「4 秒」改「2 秒」，并写清 `view_phase` 是按设备时钟算出的
    相位、不是回读屏幕内容；
  - `firmware/README.md` 一处的「4 秒」改为「2 秒」；
  - 本记录：产品规则、验收 A2、历史 A2 记录注记、「claude 行闪烁」历史记录注记，以及本节。
- 验证：
  - 先加用例 `test_row_view/view_hold_is_two_seconds`，改动前运行报
    `Expected 2000 Was 4000`（失败证据）；改后
    `pio test -d firmware -e protocol_native` 49 个用例全部通过。
  - `pio run -d firmware -e esp32c3_supermini` SUCCESS，PlatformIO 报告的 Flash 占用
    80.0%（1048554 B，取自 `firmware.elf` 的 size 检查；`firmware.bin` 文件本身更大，两者口径不同）。
  - **上机实测（2026-11-13，设备 192.168.50.107）**：
    - 烧录前基线：`status` 每 400 ms 采样 `view_phase` 24 秒，转移间隔
      4004/4001/4000/4002/4200 ms（4 秒相位）。
    - 烧录：`pio run -t upload --upload-port /dev/ttyACM0`，Hash verified，1075872 B。
    - 烧录后：同法采样 26 秒，11 个转移间隔为 10×2005 ms + 首个 1804 ms（起始对齐），
      即 2 秒相位已生效；期间 `rows_rotating=true`，Claude 行仍报「登录失效」。
    - 相位翻转时主循环被重画阻塞：60 ms 采样测得 482/484/483 ms（150 ms 采样为 451–602 ms），
      约占 2 秒相位的 24%。这是主循环阻塞时长，不等于画面可读时长：u8g2 逐页发送，旧内容
      不会整屏瞬间消失，「肉眼静止段」的换算（2 秒 − 阻塞）**未经画面录像核实**。
    - 目视外观（像素级）仍需用户本人确认，API 只能证明相位与阻塞时长。
- 已知限制与本次不修（第 1 轮审查提出，均属实但属于既有行为或被本次节奏放大）：
  - 重画占空比：实机测得相位翻转阻塞 0.45–0.5 秒，按相位 4 秒 → 2 秒折算约 12% → 24%。
    （`firmware/README.md` 的「整屏约 0.9 秒」是早先按软件 I²C 码率/整屏字节数估的量，
    与本次实测的「主循环阻塞 0.45–0.5 秒」口径不同，两者差异尚未查清，不能直接把 0.9 秒
    说成上限。）
  - 若 fetch 完成后的 `drawScreen()`（`main.cpp` 1483–1489）或 60 秒空闲重绘恰好落在相位
    边界前约 0.5 秒内，会先按旧相位画完、再由 loop 的相位判断补画一次。更糟的情况是同一次
    loop 里「抓取后重画 → 相位补画 → 定时重绘」连续执行，累计阻塞约 1–1.5 秒；所以
    「单次约 0.5 秒」不是输入延迟的上限。稳态下（边界后约 5 ms 开始重画）不会仅因相位判断
    反复重画；重画时长 < 相位长度保证不会无限循环。`erase` 不在其中：`clearSettings()`
    会把各行恢复为未配置，`anyRowAbnormal()` 随之为假。
  - 阻塞抓取期间画面轮换暂停：`refreshSources()` 同步占用主循环（一次 HTTP 等待可达数秒，
    Wi-Fi 重连路径最长约 15 秒），期间不检查相位；恢复后相位按设备时钟直接跳到当前值，
    所以异常行可能超过 2 秒没切、甚至跳过若干相位。2 秒是相位长度，不是网络等待期间的
    轮换保证。
  - 重画期间主循环被 `sendBuffer()` 阻塞约 0.45–0.5 秒，`processSerial()`/`updateKeys()` 不跑：
    串口命令只是延迟（CLI 超时 12 秒），`#` 按键若整段落在阻塞窗口内会被漏掉。
    需要把按键轮询或 I²C 传输挪出主循环才能根治，属于独立改动。
  - 无数据的异常行 `showStatusView` 恒为视图 2，屏幕内容不随相位变化，但
    `anyRowAbnormal()` 仍每 2 秒触发一次无视觉收益的全屏重画（实机约 0.45–0.5 秒阻塞，
    相位重画占用约从 12% 增到 24%）。
    可用 `abnormal && hasData` 单独作为「是否需要轮换重画」的条件；本次按最小改动不改，
    留作后续优化（改完要重新上机看画面）。
  - `view_phase` / `rows_rotating` 保持既有语义（本次目标里写明不改）：前者由
    `viewPhase(millis())` 算出、不是 `drawnPhase`，无数据的异常行常驻视图 2 时它仍报交替。
    本次只把 README 的描述改准确（见上），不改字段行为。
